## 0. Перед началом

- Ветка `refactor/collector` смержена в `main` и задеплоена. С `COLLECTOR_MODE=off` (по умолчанию) поведение прода не меняется: новые таблицы ядра пустые, расписание сборщика и приём выключены.
- CI зелёный: PHPUnit, pytest парсера, сборщик (ruff, mypy, pytest с MySQL, сборка образа).
- Нет идущего прогона старого парсера, если шаг это требует (см. ниже).

## 1. База и пользователь сборщика (один раз)

Выполнить под root в контейнере MySQL (`railway ssh` в `MySQL-6oyM`). Пароль сгенерировать, в git и чаты не писать.

```sql
CREATE DATABASE IF NOT EXISTS collector CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'collector'@'%' IDENTIFIED BY '<сгенерированный пароль>';
GRANT ALL PRIVILEGES ON collector.* TO 'collector'@'%';
-- узкие каналы к схеме ядра (docs/adr/0001)
GRANT SELECT ON railway.parse_filters TO 'collector'@'%';
GRANT SELECT, UPDATE (status, progress, result, updated_at) ON railway.parse_jobs TO 'collector'@'%';
FLUSH PRIVILEGES;
```

Ядро читает `collector.ingest_lots` своим пользователем (сейчас root — права уже есть).

Эти права проверены на модели схемы (MySQL 9.1, 21.10.2026): миграции, захват задачи `FOR UPDATE SKIP LOCKED`, прогресс и итог, чтение правил работают; чтение `lots` запрещено. Новые пользователи MySQL 9 используют `caching_sha2_password` — сборщику для этого нужен пакет `cryptography` (уже в зависимостях).

## 2. Сервис `collector` в Railway

| Настройка | Значение |
|---|---|
| Источник | тот же репозиторий, ветка `main` |
| Root directory | `collector` |
| Dockerfile | `collector/Dockerfile` |
| Watch paths | `collector/**`, `contracts/**` |
| Том, публичный домен | не нужны |

Переменные:

| Переменная | Значение |
|---|---|
| `COLLECTOR_DATABASE_URL` | `mysql+aiomysql://collector:<пароль>@mysql-6oym.railway.internal:3306/collector` |
| `COLLECTOR_CORE_SCHEMA` | `railway` |
| `COLLECTOR_CLAIM` | `tagged` (теневой режим) |
| `FLOPPY_USERNAME`, `FLOPPY_PASSWORD`, `FLOPPY_HOST` | ссылки на переменные веб-сервиса |
| `COLLECTOR_CONCURRENCY`, `COLLECTOR_HISTORY_CONCURRENCY` | `25` по умолчанию (у старого парсера было `ENCAR_WORKERS=15`) |
| `COLLECTOR_PROXY_SESSIONS` | `30` по умолчанию: сессий прокси больше, чем запросов в полёте |
| `COLLECTOR_PIPELINE_DEPTH` | `3` по умолчанию: страниц в работе одновременно; следующая грузится, пока у предыдущих догружается история |
| `COLLECTOR_HISTORY_MAX_AGE_HOURS` | `48` по умолчанию: история старше перекачивается, кроме старейшей трети (`ENCAR_HISTORY_EVERY_RUNS`); проверка 23.10.2026: до 3 дней расхождений не было, 3–7 дней — ~1 % |
| `COLLECTOR_HTTP_TIMEOUT` | `12` с по умолчанию: дольше висит только «застрявший» выход прокси, запрос повторяется через другую сессию |
| `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` | `40` — **обязательно**: по умолчанию Railway даёт 0 с между SIGTERM и SIGKILL |
| `COLLECTOR_STOP_GRACE_SECONDS` | `25` (по умолчанию): сколько после SIGTERM дорабатывает текущая страница |
| `COLLECTOR_STALE_MINUTES` | `10` (по умолчанию): задачу, оставшуюся `running` без прогресса, сборщик забирает обратно |
| `LOG_LEVEL` | `INFO` |

Первый старт применяет миграции схемы `collector` и ждёт задач.

Остановка (деплой сборщика): по SIGTERM текущая страница дорабатывает до `COLLECTOR_STOP_GRACE_SECONDS`, затем отменяется; задача уходит в `interrupted` с чекпоинтом (сегмент и следующая страница), следующий процесс продолжает с неё. Лоты, уже записанные прогоном, повторно не считаются (`ingest_lots.run_id`), так что покрытие не завышается. Если процесс убит раньше, задача остаётся `running`, и через `COLLECTOR_STALE_MINUTES` без прогресса сборщик забирает её сам. Задачи старого парсера (без отметки `collector` в прогрессе) так не забираются.

## 3. Теневой режим

Веб-сервис: `COLLECTOR_MODE=shadow`, `COLLECTOR_DB_DATABASE=collector` (хост и пользователь — как у `DB_*`).

Что происходит:
- `collector:enqueue` ставит сборщику полные прогоны по `parser_schedules` с тегом `filters.engine=collector`.
- Старый парсер работает как раньше и не видит этих задач; `lots:lifecycle` и проверки «идёт прогон» их тоже не видят.
- Записи сборщика копятся в буфере, но в `lots` не применяются.

Стоимость: два обхода → примерно вдвое больше трафика прокси на время тени. Первый прогон сборщика тянет историю всех лотов (своей истории у него ещё нет) — по длительности как старый полный прогон; дальше история перепроверяется по трети за прогон, а отклонённые лоты больше не перекачиваются.

После каждого прогона сборщика:

```bash
php artisan collector:compare
```

**Критерии приёмки** (минимум 3 прогона за 2 суток):

| Показатель | Порог | Почему не ноль |
|---|---|---|
| Покрытие (`coverage_pct` в задаче) | не ниже, чем у старого парсера, −2 п. п. | — |
| `price`, `mileage` | ≤ 3 % / ≤ 1 % | прогоны видят объявление в разное время |
| `vin`, `engine_volume` | смотреть примеры | сборщик отбрасывает мусор (VIN не 17 символов, объём > 10 л) |
| `is_active` | каждое расхождение объяснимо | старый парсер «мигал» на правиле страховых случаев |
| прочие поля | ≤ 0,5 % | — |
| `only_parser_active` | ≤ 2 % активных лотов | снятые между прогонами |

Плюс в задачах сборщика: `history_failed` и `detail_failed` не растут, `errors` близки к нулю.

## 4. Переключение (одним окном, без идущего прогона)

1. Дождаться, пока нет задач в `running` (ни старых, ни сборщика).
2. Веб-сервис: `COLLECTOR_MODE=primary`, `PARSER_ENABLED=false`.
3. Сборщик: `COLLECTOR_CLAIM=all` (берёт и задачи без тега, оставшиеся с прошлого).
   В `primary` каждая новая задача (кнопка прогона и перепарсинг в админке, `collector:enqueue`) создаётся с тегом `engine=collector`, поэтому учитывается `lots:lifecycle` и проверками «идёт прогон».
4. После старта веб-сервиса — один раз:

   ```bash
   php artisan ingest:cutover
   ```

   Отметка ядра переходит в конец буфера (теневые записи не применяются), а точка переключения запоминается: `lots:lifecycle` никогда не засчитает теневой прогон.

   Если теневого режима не было, своей истории у сборщика нет, и первый прогон перекачал бы запись и осмотр каждого лота (около суток). Перенести её из `lots` один раз:

   ```bash
   php artisan collector:seed-history
   ```
5. Следующий прогон сборщика наполняет `lots` через буфер (`ingest:consume` раз в минуту). До его завершения `lots:lifecycle` ничего не снимает: успешных прогонов после переключения ещё нет.
6. Проверить: `php artisan lots:lifecycle --dry-run -v` показывает прогон сборщика, засчитанный только после `ingest pending` → применён.

## 5. Деплой без простоя

После суток стабильной работы в `primary`:
- снять том `/app/logs` с веб-сервиса (логи прогонов теперь в `collector.run_log`);
- выставить `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS=35` и readiness-healthcheck `/up`.

Деплой веб-сервиса больше не обрывает прогоны (они в другом сервисе) и не даёт 502 (нет тома).

## 6. Откат

- В любой момент до этапа 7: `COLLECTOR_MODE=shadow` (или `off`), `PARSER_ENABLED=true`, сборщику `COLLECTOR_CLAIM=tagged`.
- Старый парсер снова кормит `lots` со следующего прогона; `lots:lifecycle` снова считает его прогоны.

## Известные доработки

- Страница «Логи» админки: показать `collector.run_log` для задач сборщика (сейчас лог виден в прогрессе задачи и в логах сервиса Railway).
- Инкрементальный обход (частый проход по новым и изменённым, редкий полный) — после стабилизации.
- Список марок брать из фильтр-API Encar, а не из глобального прохода. Глобальный проход по `ModifiedDate` сдвигается, пока идёт (за минуту поднимаются десятки объявлений), и иногда обрывается на защите «страница целиком уже видена». Марки, не попавшие в первые страницы, тогда не обходятся. Так же было у старого парсера (покрытие 93–97 %).
