# Рефакторинг: сервис-сборщик (collector) и ядро (core)

> Ветка `refactor/collector`. Каждый этап закрывается тестами и не ломает прод:
> старый парсер работает, пока новый сборщик не докажет паритет (этап 6).

---

## Зачем

Цифры с прода на 21.10.2026:

| Проблема | Факт |
|---|---|
| Полный прогон Encar | 5–12,5 ч; любой деплой сайта его обрывает (общий контейнер) |
| Деплой сайта | 502 несколько минут: на веб-сервисе висит том, Railway не умеет zero-downtime с томом |
| Мигание лотов | ~34 тыс. лотов каждый прогон пишутся дважды: после деталей (истории ещё нет, PRE-правило `max_insurance_count` не срабатывает → `is_active=1`, событие `relisted`) и после истории (правило срабатывает → `deactivated_filter`). ~65 тыс. мусорных строк `lot_changes` в сутки. Историю отклонённых лотов не хранят, поэтому они перекачиваются **каждый** прогон — лишний трафик прокси |
| Сырые ответы | Не хранятся (`raw_data` ≈ 200 байт). Любая правка разбора = перекачка 200 тыс. лотов |
| Тесты парсера | 27% покрытия; 13 падают (живой Encar под геоблоком, мёртвый KBChacha) |
| Мёртвый код | ~4,5 тыс. строк из 14 тыс. (KBChacha, разовые скрипты, `reparse_worker`, ветки Encar) |
| Связь Python ↔ Laravel | Не зафиксирована: два пути записи (HTTP upsert и прямой pymysql), два планировщика, правила отбора в двух реализациях |

## Целевая схема

```
┌──────────────── collector (Python, отдельный сервис Railway) ───────────────┐
│ ports & adapters:                                                            │
│   SourceAdapter[Encar | …]  →  Pipeline (pre-rules → details → post-rules)   │
│   RawStore (bucket)  JobSource  IngestSink  ProxyPool  Clock                 │
│ своя схема MySQL `collector`: raw-индекс, курсоры, чекпоинты, логи прогонов  │
└───────────────┬───────────────────────────────────────▲─────────────────────┘
                │ CarLot v1 (JSON Schema) → ingest_lots  │ команды (parse_jobs),
                ▼                                        │ настройки (internal API)
┌──────────────── core (Laravel, сервис web) ─────────────┴─────────────────────┐
│ ingest consumer (идемпотентный, по хэшу) → lots / lot_changes (доменные       │
│ события) → нормализация, каталог, жизненный цикл, поиск, API, админка         │
└───────────────────────────────────────────────────────────────────────────────┘
```

Решения с обоснованием — в [`docs/adr`](../adr/).

## Этапы

Каждый этап — отдельные коммиты в ветке, у каждого критерии готовности. Этапы 1–5
не трогают прод; этап 6 включает новый сборщик рядом со старым.

### Этап 0 — Фундамент
- [x] Разобрать мигание лотов (причина выше; исправление — этапы 2–4: правила считаются на полном лоте, запись одна; состояние истории хранит сборщик).
- [ ] CI (GitHub Actions): PHPUnit + pytest + линтеры на каждый push/PR.
- [ ] Инструмент записи эталона: сохранить настоящие ответы Encar ~1 000 лотов (на Railway через прокси) и вывод старого парсера по ним.

**Готово, когда:** CI зелёный; в репозитории лежат записанные ответы и эталонный вывод старого парсера.

### Этап 1 — Каркас сборщика и контракт
- `collector/` — пакет на uv, Python 3.13, ruff, mypy `--strict`, pytest + coverage.
- Доменная модель `CarLot` v1 (Pydantic v2) → генерация `contracts/carlot.v1.schema.json`.
- Контрактные тесты: Python валидирует свой сериализованный вывод, PHP — фикстуры по той же схеме; проверка обратной совместимости схемы.

**Готово, когда:** схема сгенерирована и проверяется с обеих сторон в CI.

### Этап 2 — Приём данных в ядре
- Схема `collector`, таблица-буфер `ingest_lots` (источник, ID, версия контракта, JSON, хэш, run_id).
- Laravel-консьюмер: валидация по схеме, идемпотентный upsert в `lots`, `lot_changes` через доменные события, итоговый `is_active` за одну запись.
- Отдельные пользователи MySQL с минимальными правами.

**Готово, когда:** feature-тесты на MySQL покрывают вставку, обновление, повтор пачки, битую запись, снятие/возврат лота; мигание невозможно по построению.

### Этап 3 — Адаптер Encar
- Асинхронный клиент (httpx), лимиты на хост, повторы с backoff, ротация прокси.
- Маппинг ответов → `CarLot` на записанных фикстурах.
- Правила отбора в конвейере сборщика: PRE до деталей, POST на полном `CarLot`, вердикт едет в контракте.
- Паритет с эталоном старого парсера: расхождения = 0 или каждое объяснено.

**Готово, когда:** паритет-тест зелёный, покрытие доменной части ≥ 90%.

### Этап 4 — Оркестрация
- Задачи только из ядра (`parse_jobs`), APScheduler удаляется.
- Возобновляемые прогоны: чекпоинты по страницам, корректная остановка по SIGTERM — деплой больше не убивает прогон.
- Инкрементальный обход (новые/изменённые по дате) и редкий полный проход для снятия.
- Прогресс и логи прогона — в БД, а не в файл на общем томе.

### Этап 5 — Сырой слой
- RawStore: последний ответ на лот и тип запроса, сжатый, в бакете Railway; запись только при смене хэша.
- Команда повторного разбора (replay) без запросов к бирже.

### Этап 6 — Теневой запуск и переключение
- Сборщик — отдельный сервис Railway в теневом режиме: пишет только в буфер, ядро сравнивает с данными старого парсера; отчёт о паритете в админке.
- Переключение: ядро принимает данные сборщика, старый парсер выключается, том снимается с web, включается перекрытие деплоев.

### Этап 7 — Уборка
- Удалить `parser/` целиком (включая KBChacha), обновить документацию.
- Почистить мусорные строки мигания в `lot_changes` (только с подтверждения).
